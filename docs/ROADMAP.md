## 阶段一：把「单点判定」变成「时间序列」判定

**这是当前最大的短板。** 现在 `list.meta.cn.yml` 是用最近 N 轮（默认 6 轮）做的判定，
但判定口径是「取最近 N 轮」，而**节点池在轮次之间是漂移的**——每轮进来一批新地址、
走掉一批旧地址。于是：

- 同一个地址可能在第 3 轮才出现，第 4 轮就消失
- 「跨轮全活」要求的轮次连续性实际上拿不到，`min_rounds=2` 退化成「最近两轮都活着」
- 节点数会随历史积累缓慢下降，但这个下降反映的是**轮次连续性**而不是**真实质量**

**要做的事：**

1. 把「按地址聚合**所有**历史轮次」做成判定基础，而不是「取最近 N 轮」
   - 一个地址在历史上出现过 M 轮、其中存活 K 轮
   - 判定改为「K/M ≥ 阈值」，M < 2 时判「未定」保守保留
2. 阈值从 `alive_ratio` 扩展为「至少 K 轮存活」+「存活率不低于 R」
3. NAS 侧把探测历史**长期保留**（现在只留 20 份，且分支被覆盖）

**验收标准：**

- 连续 3 天的 `crosscheck_summary.md` 里，「国内跨轮全活」的数字**不再单调下降**
- 同一批节点在多轮之间的「可用」判定稳定（抖动 < 10%）

## 阶段二：按协议动态决定排序与取舍

现在 `protocol_order` 是写死的实测值（vmess > vless > trojan > ss）。但 NAS 那边
每天都在产生新的协议维度数据，应该**由数据驱动**而不是人工维护。

**要做的事：**

1. NAS 侧按协议统计国内可用率，产出 `protocol_stats.csv`
2. CI 据此自动生成排序（仍允许在 `fetch_config.local.yml` 里手工覆盖）
3. 顺带产出「按协议推荐配置」——比如 ss 可用率长期低于 20% 时，
   在 `list.meta.cn.yml` 里直接不推 ss，只在「全量」里保留

**验收标准：** 排序与取舍无需人工干预地随数据变化。

## 风险清单

| 风险 | 影响 | 缓解 |
| :- | :- | :- |
| NAS 停机 / 重启 | 大陆版停止更新，最后一版一直挂着 | 监控 `probe.log` 的时间戳；或加个「超过 12 小时未更新」的告警 |
| GitHub schedule 不准时 | 产物延迟 | 手动触发兜底；`workflow_dispatch` 已配 |
| 上游源结构变化 | 抓不到节点 | `list_result.csv` 会显示每个源的节点数，异常一眼可见 |
| 判定口径漂移 | 节点数莫名变化 | 交叉表里「参与判定的轮次」和判定汇总能看出来 |
| 订阅被投毒 | 注入恶意节点 | 只用 GitHub 原始 URL；配置片段来自自家仓库 |

## 明确不做的事

- **不做主动投毒检测** —— 服务端探针只能判断「通不通」，判断不了「内容是否恶意」
- **不做节点内容审计** —— 同上
- **不追求「节点越多越好」** —— 实测证明加节点不等于加可用节点
- **不改上游 `config.yml` 的规则集** —— 靠 sync 工作流的差异报告人工合并
